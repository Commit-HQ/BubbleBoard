# Architecture

One SvelteKit application, deployed as one Cloudflare Worker with static assets. Keep client code in `src/lib`, server-only helpers in `src/lib/server`, and HTTP endpoints in `src/routes`. Use strict TypeScript and Svelte 5 runes. Module-level constants such as lookup tables and asset lists are fine; never keep per-user or per-request mutable state at module level on the server.

## Boundaries

- Browser: card reading, key derivation, encryption and decryption, and later photo processing, in the [access format](access-format.md). `src/lib/kindergarten.ts` opens and builds the records, and `src/lib/app/state.svelte.ts` holds what a device may see and the changes it makes.
- Worker: sessions, authorization, request checks, and storing ciphertext (`src/lib/server`, `src/routes/api`); and notifications without content, sent through a queue (`src/lib/server/push.ts`), whose handler, with the daily cleanup (`src/lib/server/cleanup.ts`), `worker/index.js` adds to SvelteKit's fetch handler.
- D1: opaque identifiers, hashes of card and session tokens, and encrypted records, with the schema in `migrations/`. `npm run deploy` publishes before migrating, because the first deploy creates the database, so keep each migration compatible with the code already running.
- Private R2: encrypted photos and files, fetched through authorized Worker routes: the photo of each classroom's board (`src/lib/server/photos.ts`) and the files on notices (`src/lib/server/notices.ts`). Every read and write goes through `src/lib/server/storage.ts`, which counts each object's bytes and each month's uploads and downloads in D1 before R2 is touched, and refuses more past the `STORAGE_*` limits in `.env` (`src/lib/server/limits.ts`), so an installation stays within R2's free allowance. Records name the objects they keep (the `named_objects` view in `migrations/`, which each new kind of record that keeps bytes joins, with a trigger that marks its object as on its way out when the record goes, however it goes); a change deletes the objects it marked once it's saved, and the daily cleanup deletes those a change didn't finish, and uploads no record named a day later. A key is stored only once, and an object is marked as on its way out before its bytes are deleted, so no upload replaces bytes a record names and no record names bytes being deleted. Requests that change something run to their end even if the device disconnects midway (`src/hooks.server.ts`).

The app sets up a kindergarten, manages classrooms, teachers, children, and family cards, and puts notices, with their polls and files, and a photo of each classroom's corkboard on the board. Those photos and files are the only uploads: staff send them, encrypted in the browser, through authorized endpoints. Do not accept real classroom information until the access boundary has been reviewed and tried on real phones, and do not add public upload endpoints. Records are encrypted from the first one persisted; there is no plaintext version to migrate later.

## Pages and languages

Pages live in two route groups. `(marketing)` holds the landing pages, prerendered to static HTML without client-side JavaScript (`prerender` and `csr` in its `+layout.ts`). `(app)` holds the app: pages prerendered as static shells that then run in the browser. Their HTML carries no classroom data, and the server never renders any; protected data arrives as ciphertext and is decrypted on the device. The root layout only adds the stylesheet, favicon, and locale.

App pages are prerendered once, so a record's ID travels in the query (`/app/child?id=…`) and pages read it in the browser; IDs aren't secret. The header of a connected device's app pages links to Settings, which hold the language, and staff also get Manage, with the classrooms and teachers; until a device connects, the header has the language switch instead, as on the landing page. Every app page ends with a footer linking to the landing page, the privacy policy, and the build's commit. Prerendering starts from the default language's pages and finds the other language's through each app page's `hreflang` alternate links. The `(app)` layout creates one `App` state for every app page through context, and starts it after the first navigation, once the router can take a card or setup token out of the address bar; a link opened while the app shows changes only the fragment, which the layout also watches. App pages keep the title "BubbleBoard", so tab titles and browser history never hold a name.

On phones and tablets, the app works only once installed (`src/lib/install.ts`). iPhone and iPad connect nothing outside the Home Screen app, whose storage Safari doesn't share, and show how to add it; Safari keeps a card link's fragment in the address bar there, and those browsers get a manifest without `start_url`, so the Home Screen app opens at the card link it was added from and connects with that card, once. Android connects in the browser, whose storage the installed app shares, then asks to be installed; browsers inside other apps ask to open the page in a real browser. Computers use the app in the browser. Each language has a web app manifest (`/app/manifest.webmanifest`, `/en/app/manifest.webmanifest`) with the same app ID and scope, which the Worker renders because it depends on the browser asking, and its icons in `static/icons` are renderings of `src/lib/assets/app-icon.svg`.

The service worker (`src/service-worker.ts`) handles notifications only and caches nothing. Every push shows the same words, as the notification's title, in the language notifications were turned on in, which `src/lib/notifications.ts` keeps in IndexedDB for it; devices already say which app a notification is from. A push also tells the app's open windows to load the board again, and a tap brings a window forward, telling it the same, or opens the app. Turning notifications on asks for permission straight from the tap, as Safari requires, then subscribes with the installation's public VAPID key. The app sends its subscription whenever it opens, which keeps it with the current session, and loads the board again when it comes back into view. A subscription made with an earlier key gets no pushes, so the app renews it with the installation's current key first; a browser that won't subscribe without a tap ends it instead, and notifications show as off until they're turned on again. Brave refuses to subscribe until its privacy settings allow Google's push service, which Chromium browsers push through, so when subscribing fails there the app names that setting.

Croatian is served at `/` and `/app`, English at `/en` and `/en/app`; the optional `[[locale=locale]]` route segment and `src/params/locale.ts` keep the default language unprefixed. `src/lib/paths.ts` builds every path, including the language switch's link to the same page in the other language, and `src/lib/card.ts` writes and reads card codes and their links. Card links are read by their origin and fragment only, so printed cards keep working in either language; `/app` and `/en/app` must always open the app. The language switch, in the landing page's header and in the app's Settings, or its header until a device connects, is a plain link, so no cookie is needed. `src/hooks.server.ts` and the root layout take the language from the path (`pathLocale`), so an address no page has gets the root error page, a popped bubble, in the language the address asks for.

The landing page is identical on every installation: it names no kindergarten, and its contact details belong to the project (`src/lib/project.ts`). It describes the finished product in the present tense, while README tracks what is implemented. Its main action opens the app, where families connect with their card, and a second link leads kindergartens without BubbleBoard to the contact section.

The privacy policy (`/privacy`, `/en/privacy`) is a landing page too: a few short points on what an installation stores, where, and for how long, with the project's contact address. It describes what the code does (`privacyPolicy` in both dictionaries), so update it in the same change as anything that alters those. The session cookie is the only cookie and is strictly necessary, so there is no consent banner; keep it that way.

Canonical URLs, `hreflang` alternates, and link-preview tags need an absolute address, which prerendered pages can't take from a request. It comes from the required build-time `PUBLIC_SITE_URL` in `.env`, read with `$env/static/public`; Worker `vars` don't exist at build time and can't change generated HTML. `src/lib/project.ts` accepts only an `https://` origin (or `http://` for localhost) without credentials, path, query, or fragment, and otherwise stops the build with a message. Build absolute links with its `absoluteUrl`. The storage limits are build-time settings in `.env` too, read with `$env/static/private` one variable at a time, so the rest of the build machine's environment stays out of the bundle; modules the daily cleanup imports can't read them, because Wrangler bundles those without SvelteKit.

All interface copy lives in `src/lib/i18n/en.ts` and `hr.ts`. Croatian must satisfy the same TypeScript shape as English; add each new key to both dictionaries. Keep sentences whole rather than assembling translated fragments: copy that names something is a function in each dictionary, so each language builds its own sentence, plural, and list (`Intl.PluralRules` and `Intl.ListFormat`). Keep links out of translated strings: put the linked words in markup, as the footer does for Commit. User-authored classroom content is not automatically translated. The interface calls a card a QR code ("QR kod"), which parents understand; code and docs keep the word card.

## API

JSON endpoints live in `src/routes/api`, one small handler per user action. A handler first checks who is asking (`requireIdentity`, `requireStaff`, or `requireAdmin`, or `limitAttempts` for setup and cards, in `src/lib/server/session.ts`), reads its body with the readers in `validate.ts`, and makes the change through `catalog.ts`, where each change is one D1 batch and so one transaction. An admin's change takes the `Admin` that `requireAdmin` returns, so a change can't skip the check, and responds with the records as they are now; a staff session comes with its records too, so the app never asks for them separately. Record IDs in paths must match `src/params/id.ts`. The server can't read profiles, so it enforces structure: who may ask, the form of every field, foreign keys, a trigger that keeps an admin, and a catalog revision. A change to a teacher, children, or family cards names the revision its device read, and the database refuses it when another change came first, so two admins can't undo each other's work, and a form left open can't restore rights another admin withdrew. Errors are `error(status, code)`, and the app explains each code in both dictionaries (`app.errors`).

## Dependency policy

Use platform APIs and Svelte first. Add a library only for an implemented need, after checking maintenance, licensing, bundle cost, and transitive dependencies. Tailwind CSS is the styling standard. No component UI library, ORM, global state package, date library, analytics, remote fonts, or image editor is needed for this foundation.

`qr` (MIT, no dependencies) encodes cards' QR codes, which `src/lib/app/qr.ts` draws as a bubble full of SVG dots with the app icon, and reads them from the camera (`qr/dom.js`) or a photo. Its decoder loads only when someone scans a card, and `qr.test.ts` reads the drawing back with it. Tiptap 3 (MIT, on ProseMirror) is the notice editor, imported only when the notice form's editor mounts. Its injected stylesheet is off for the CSP, with its rules in `app.css`, and boards don't use it: they render a notice's checked JSON document with Svelte components (`NoticeBody.svelte`). Load future photo tooling only in the routes that use it.

Vitest is the one test runner, a development dependency only. It reuses the Vite and SvelteKit configuration, so tests import `$lib` modules as the app does, and it runs the same Web Crypto API in Node. Test behavior the code guarantees, such as encryption, card links, and authorization, not component markup. Database tests run the real migrations in Node's built-in SQLite behind a small D1-shaped adapter, with R2 in memory (`src/lib/server/catalog.test.ts`), which keeps them fast and needs no Workers runtime.

## Design

The look is cheerful glassmorphism: translucent white surfaces over soft coral, violet, sky, and sun gradients, with ink pill actions. Style with Tailwind CSS utilities in markup; Prettier sorts the classes. `src/lib/styles/app.css`, the only stylesheet, holds the theme tokens (`ink`, `muted`, `canvas`, `accent`, `blush`, `apricot`, `font-sans`, `font-display`), the utilities below, and base styles. Prefer theme tokens and Tailwind's default scale over arbitrary values, and avoid component `<style>` blocks unless Tailwind cannot express the rule.

- `glass` is the surface for cards and sections. It has no backdrop blur, which over the soft page backdrop would look nearly the same and cost painting while scrolling. It creates no stacking context, so add `isolate` when a child uses a negative z-index.
- `frosted` adds the blur, with a nearly opaque fallback where `backdrop-filter` is unsupported. Use it only where content moves or sits behind the surface: the sticky header and overlays on photos.
- `bg-sunrise` is the decorative brand gradient for icon tiles. `text-sunrise` is its version for heading text, with darker stops, and falls back to plain text in forced-colours mode.

App screens reuse these surfaces: `glass` panels and tiles, the buttons, fields, and checkboxes drawn as cards in `src/lib/app/ui.ts`, `bg-sunrise` icon tiles, and a few static soap bubbles. Printed pages drop the backdrop and surfaces (`app.css` and `print:` variants): card sheets come out on white, two cards to a row with a dashed edge to cut along, so a classroom's cards take little ink. Questions before a change that can't be undone use the native `<dialog>` (`ConfirmDialog.svelte`), as does a board photo or a notice's picture on the whole screen (`PictureViewer.svelte`); forms read `FormData` when submitted.

Palette colours are not automatically text colours: blush and apricot are too light for text on this page. Check text contrast (4.5:1, or 3:1 for large headings) against the tinted backdrop, not only the canvas. Don't let colour alone mark a state; forced colours remove fills.

Fonts are final: Hedvig Letters Serif for headings and Hanken Grotesk for text, self-hosted from Fontsource files (OFL) and never loaded from a font CDN. `app.css` declares only the Latin and Latin Extended subsets, with metric-matched local fallbacks (Arial and Georgia, values from Capsize) so text doesn't shift when the fonts swap in. `src/hooks.server.ts` preloads the Latin files on every page and the Latin Extended files on Croatian pages; app pages, which open with body text, skip the display font.

Photos are real stock images committed pre-optimized as AVIF/WebP, with sources and processing notes in `src/lib/assets/photos/CREDITS.md`. `src/lib/components/Photo.svelte` lists them by name, so a wrong name fails type checking and a missing file fails the build. Give each placement a `sizes` value that matches its layout, and set `eager` only on the photo in the first view. Only the landing page uses stock photos; the app shows only the photos teachers take of their boards and the pictures they attach to notices, decrypted in the browser. Icons come from `src/lib/components/Icon.svelte`. Photo, font, icon, and library licenses are in `static/third-party-notices.txt`, which every installation serves; update it when bundling a new asset or library. No remote images, remote fonts, or animation library.

Use semantic HTML, visible focus, comfortable touch targets, responsive layouts, and reduced-motion support. Only real links should look and behave like links. A link that leaves the app, such as About BubbleBoard, a build's commit, or a link in a notice, opens in a window of its own (`target="_blank"`), because the installed app has no way back. Long words break anywhere (`overflow-wrap: anywhere` in `app.css`), so user content such as a file's name or a link never widens a page; don't set `nowrap` on it. Extract components when they represent a reusable concept, not simply to split a file. Keep parent flows short and use defaults instead of repeated configuration choices. App pages show a real loading state while they start, and errors say what to do next in both languages.

## Security direction

The target is protection of stored content without server-held decryption keys. An operator who can modify delivered JavaScript remains trusted. Client compromise, shared QR cards, and saved photos remain outside that protection. Revocation blocks server access; it cannot erase retained keys or downloaded content. Every staff card opens the same Staff Key, so teachers are kept to their classrooms by authorization, not encryption ([access format](access-format.md)); check every new endpoint and query against that.

A hash-mode CSP (`csp` in `vite.config.ts`) allows same-origin resources only, and images from the `blob:` URLs the app makes for photos it decrypted, no inline scripts or styles beyond SvelteKit's hashed ones, no plugins, and no framing. Prerendered pages carry it as a `<meta>` tag and get the other security headers, including `frame-ancestors`, from `_headers`; Worker-rendered responses get them from `src/hooks.server.ts`. Keep the two header lists in sync and keep them strict: self-host new assets rather than widening directives. App pages run SvelteKit in the browser, whose route announcer has one fixed inline style attribute: `style-src-attr` allows exactly that value by hash (`'unsafe-hashes'`, never `'unsafe-inline'`), and `src/csp.test.ts` fails when a SvelteKit update changes it. Style with classes, not inline style attributes. Documents on notices are saved as downloads, never opened in the app, with a type from a fixed list chosen by their name (`src/lib/files.ts`), so no file opens as a page with the app's origin. Pictures on notices show, as board photos do, only as JPEG, PNG, or WebP images checked by their bytes, from `blob:` URLs, and WebP is saved as PNG.

A device connects once with a card and then uses a session: a random 256-bit token in an HttpOnly, SameSite=Strict cookie limited to `/api`, stored only as its SHA-256 hash, and ending after 90 days without use. Replacing a card, or removing the teacher or family it belongs to, deletes its sessions. Requests that change something under `/api` must carry this site's `Origin` (`src/hooks.server.ts`), bodies are JSON of at most 64 KB, apart from the encrypted bytes of a board photo of at most 3 MB, with its encrypted details in a header, or of a notice's file of at most 10 MB, uploads and downloads stay within the storage limits, and setup and card attempts are rate limited per address (`CARD_ATTEMPTS` in `wrangler.jsonc`). The setup token, a Worker secret, allows only the first setup, and a setup link carries it in the fragment.

Card secrets stay in URL fragments: never put them in paths, queries, request bodies, storage, or logs. The one exception is outside the app's control: on iPhone and iPad, a card link's fragment stays in Safari's address bar so the Home Screen app can open with it, and iOS keeps that address in Safari's history and with the Home Screen icon ([access format](access-format.md)). Keys are created and used with Web Crypto as non-extractable `CryptoKey` objects; that prevents accidental export, not misuse by a script running in the app, so XSS remains critical (product-spec.md §36).

The footers of the landing page and every app page show the commit a build came from (product specification §47), marked as modified when the build had uncommitted changes, including new files Git doesn't ignore, and an unknown build when there was no Git metadata (for example, a source ZIP). A commit is provenance, not proof that a deployed tree matches it. Publishing a build manifest and verifying deployed output belong with automated deploys. Before real data: review the access boundary, try cards and browser storage on real iPhone and Android devices, document backup and restore, and review the CSP for new features; retention, deletion, and notification enrollment come with their features. Never log QR secrets, tokens, plaintext content, or request bodies. Keep push text generic: pushes carry no content, go only to the push services browsers use, and are signed with the installation's `VAPID_KEY` secret, which is never replaced, because devices subscribe with its public key. Cloudflare never shows a secret again, so `scripts/push-key.js` shows a new key once, to be kept in a password manager. No third-party runtime scripts or user-controlled HTML.

The [product specification](product-spec.md) holds the requirements. It is the original target, not a statement of implemented guarantees, and its opening note lists the decisions that have since replaced parts of it. Follow that note where they differ, and reconcile the rest with it before implementing a feature.

## Dependency audit

On 2026-09-11, `npm audit` reported one low-severity advisory in SvelteKit’s transitive `cookie` dependency ([GHSA-pxg6-pf52-xh8x](https://github.com/advisories/GHSA-pxg6-pf52-xh8x)), propagated to three package entries, and it still did on 2026-09-12. The suggested automatic fix downgrades SvelteKit incompatibly, so it was not applied. The advisory concerns cookie names, paths, and domains taken from untrusted input; the session cookie's name, path, and attributes are fixed in `src/lib/server/session.ts`. Keep them fixed, and recheck upstream when updating SvelteKit.
