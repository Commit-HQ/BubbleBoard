# Event photo format 1

How an event's photos are encrypted so that a family's device can compose exactly the photo it may see, and nothing more. Annual albums and republication are out of scope. The [editor](events-editor.md) covers the workflow above it.

## Encryption and rendering

An event has a fresh AES-GCM key. Its raw key is sealed with the classroom Group Key (`event-key`). The event manifest (`event-content`) contains format, title, date, description and ordered photo IDs/dimensions, each photo optionally carrying up to 300 characters of the teacher's own words. The description is a checked notice document (`src/lib/notices.ts`), read through the same reader boards use for notices and rendered with the app's own components, never as HTML. Each photo is one binary AES-GCM envelope (`event-photo`) in private R2. Inside it are a compressed base (WebP, or JPEG where a browser can't write WebP) with every marked rectangle overwritten, its encoding named beside it, encrypted lossless PNG face patches, anonymous recipient grant envelopes and a Staff-Key envelope containing labels, geometry and all patch keys. Original files and camera metadata are not uploaded. A device composes the photo it shows from the base and the patches it can open, and compresses that too: the composite is never uploaded, and what a family saves from the viewer is a JPEG of it.

Every new context uses additional authenticated data `['BubbleBoard',1,purpose,event,photo-or-null,part-or-null]`; existing card/data contexts remain byte-for-byte unchanged. `event-face` protects one patch with a fresh key. `event-grant` holds that patch key encrypted with each eligible Family Key. Group-visible patch keys are inside the event package. `event-staff` opens patch keys only for staff. Readers validate the manifest and photo dimensions; inaccessible/damaged patches leave the covered base in place. Download uses the same rendered PNG as the gallery. Event cards contain no original thumbnail.

Face patches are the cover's whole rectangle, since its corners outside the ellipse are already in the base; they zero all RGBA channels where any other cover's rectangle overlaps. Overlap cells are grouped by the exact set of covering faces and encrypted separately. A family gets an overlap key only if every involved face is group-visible or belongs to that family. An overlap key is group-visible only if all involved faces are group-visible. Areas involving an unassigned/permanently covered face never produce a patch. Bounding-box gaps in overlap patches are zero in all channels. Private face patches and overlap patches use lossless encoding: they carry faces, and the exact zeroes at their edges are what keeps a boundary where the geometry puts it. The base is compressed, because every cover's ellipse, plus a pixel so the sticker's clipped edge blends into the fill and never into the photo, is overwritten with a flat colour and its sticker drawn on before anything is encoded, so no face pixel reaches the encoder and there is nothing for compression to bleed; the reader accepts only the encodings the device may write. Caps: the installation's photo limit (30 by default, `PUBLIC_EVENT_PHOTOS`), 100 covers/photo, 400 patches/photo, 32 000 bytes of manifest, 32 MiB encrypted photo payload and 4 MiB of prepared gallery for each photo the limit allows — a photo of the editor's size packages to well under a megabyte, and its patches are what grow when it is full of children. The device measures the sealed manifest before it uploads anything, so words too long are refused before the photos are sent.

## Consent and publication

`photo_families` projects each child's name under the linked Family Key using `photo-label` with child/family IDs. A head's or a lead's child changes update projections atomically; staff sync backfills existing catalogs under an exact catalog revision. Family updates can only target an existing row belonging to their authenticated family and compare the row revision. A head or the classroom's lead records the same choice from the child's page, or when a child is added, for every family card linked to the child: that write also names the row revision it read, and a parent's change made meanwhile empties the revision instead, which fails the whole child change as stale. `photo-choice` authenticates the child/family combination. Missing, malformed and unreadable choices are private. Group sharing requires an explicit true choice from every family actually linked in the decrypted catalog. Staff ignore injected/unrelated IDs.

Each classroom has its own consent revision, which advances on choice changes and projection insert/delete for that classroom's children, so a change in one classroom leaves another classroom's preparation alone. A child moved or removed leaves its old classroom's clock where it was, but that change advances the catalog revision, which publication compares too. Preparation reads consent and catalog revisions. New event IDs reserve a draft owned by the current credential, and only that credential may upload to it; an event that is up takes photos from whoever may change it. Either way an uploaded object is unreadable until a record names it in `event_files`, and one no record names is reclaimed by the daily cleanup. Uploads are immutable, counted through `stored_objects`; HEAD checks exclude uploads that were counted but never reached R2. The publication transaction names every object and changes draft to published, with a database trigger comparing catalog and consent revisions. A changed revision fails the entire transaction and requires a new preparation/preview. Lost-response retries use the same immutable draft and cannot duplicate the event or its push. A failed R2 write requires preparing a new draft; old unreferenced objects are cleaned up. Drafts expire after one day.

Published choices are snapshots: subsequent consent edits do not change old events, and a photo already published is never sealed again, so it keeps the covers and the consent of the day it went up.

The author, a head, or the classroom's lead can change an event that is up: its title, date, description, duration and each photo's own words, which photos it holds, and no more. The event keeps its content key and the envelope its classroom opens that key with, so a change simply seals the manifest again. Changing a published photo's covers is done within that rule: the staff device puts the photo back together from its base and the patches the Staff Key opens (`restorePackage`), which is the whole picture less the faces kept covered when it went up, whose pixels were painted over before encoding and exist nowhere. The editor treats the result as a new photo with the old one's words and covers, and the change publishes it under a new ID in the old one's place and takes the old one off. The bytes at a published path therefore never change, a reopened photo carries today's consent for every face in it, and a copy a family saved from the earlier version stays with them, while the copy their device composed goes with the next load of the board's events, as any photo taken off does. The base is re-encoded each time this happens; the faces come from lossless patches and lose nothing. Photos added now are prepared against the consent and catalog as they stand when they are added, and the change names those two revisions; because the publication trigger compares revisions only as an event first goes up, the change compares them itself, and refuses the whole transaction as stale unless both still match — a parent who changed their mind while the photos were being prepared is never published under the old answer. A change that adds no photos depends on no consent and compares nothing. An event must keep at least one photo, since its board card is the first of them; an event that should keep none is removed instead. Nobody is notified again, the event keeps its place on the board, and `edited_at` marks it as changed wherever it is shown. Removal/expiry denies new reads immediately; named-object deletion triggers and daily cleanup reclaim the encrypted bytes, and a photo taken off in a change goes the same way. Duration is 1/3/7/14/30/60/90 days from publication. No hidden archive. The author, a head, or the classroom's lead can remove an event, subject to current classroom access. Every fetch requires an active session and current classroom membership, with private/no-store responses. The gallery releases object URLs and hides expired events. A device keeps each photo it composed, unencrypted, for the card that composed it (`src/lib/events/cache.ts`): the card's own keys are unencrypted in the same IndexedDB, as the editor's draft is, so encrypting the copies would protect nothing. They are found by the path the sealed bytes come from, which is enough because a published photo is never sealed again. Every load of the board's events lets go of the copies of photos no event still up holds, so a removed or expired event, or a photo taken off in a change, leaves the device with the next load, and disconnecting clears them all. A copy already composed on a device, or saved from it, cannot be recalled.

## What families see

A gallery is a grid of small squares, three across on a phone and more on a wider screen, and every square is a small copy, made on the device, of this family's own composed photo: the server holds no thumbnail and never makes one, and thirty photos drawn at full size would be more decoded pixels than an older phone can hold. The squares fill in one at a time (`src/lib/events/gallery.ts`), nearest the photo being looked at first, so a visit fetches each photo once through the app's picture cache, never in parallel, and stops the moment the family leaves the page or opens another event. A photo the device composed before comes from the device without being fetched. A square that didn't open says so and is tried again when tapped. A tap opens the photo on the whole screen, where a swipe moves through the gallery, the teacher's words show underneath, and Save keeps the composed JPEG; Share hands that same file to the device's share sheet where there is one, which is nothing a family couldn't already save. The board's event card shows the first photo the same way, opened only once the card is nearly on the screen, and falls back to the card's words if it doesn't open.

`renderPackage` also says whether any of a photo's grant envelopes opened with this card's Family Key, which marks the photos this family's own child is in, with a button to show only those. A face is granted to its own families whether or not the classroom may also see it, so a shared face still says so, and an overlap's envelope goes only to a family linked to a face in it the classroom may not see; both therefore mean the same thing. The marks are worked out while composing, entirely on the device, and the envelopes are only opened until the first one does, so knowing costs nothing after that. The device cannot tell which of its children a face belongs to — a grant names no child — so the mark says "your child" and never a name. Staff see every face and so get no marks. Nothing about this is sent anywhere: the server still sees only sealed bytes and cannot tell which family fetched which photo's faces.

The gallery says when the photos come down (`expiresAt`), and the board's card says the same in short. Under a family's gallery, one line explains that a sticker covers the children whose families keep their photos to themselves, and links to Settings, where that choice is made. Publishing an event sends the `photos` push kind, whose letter is `p`; a service worker that predates it reads an unknown letter as a notice and shows the notice wording rather than nothing.

## Detection and verification

The pinned short-range BlazeFace model stays local in a classic worker. Full-image and overlapping half-size crops are scanned at 0/90/180/270 degrees, then duplicate boxes suppressed before padded editor covers are created. This improves scale/orientation coverage without another model dependency; no accuracy guarantee is made. On the bundled classroom photo this found six faces versus three in the previous single pass. Manual correction and teacher review are still required.

Unit/integration tests cover consent intersection, wrong keys/contexts, overlap pixel sanitization, stale publication rollback, wrong-classroom reads, missing uploads, idempotent publication and cleanup. Composing a photo needs a real browser canvas, which these tests don't have, so what each family sees is checked on real devices connected with test QR codes; the development-only `/editor-check` page that once did this was removed (2026-09-21). Physical iOS/Android performance, representative real galleries and pilot acceptance remain outstanding.
